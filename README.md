# 日报助手 · 企业微信工作记录与周报

用企业微信对话收集工作计划与每日进展，由员工确认后保存，形成员工周报和团队周报，让管理者在手机上查看业务进展并反馈。

这是从已有验证项目整理出的**公开开发基线**，用于继续开发和迁移至新的服务器。仓库包含可运行的机器人、业务服务、移动端周报、测试与部署配置；不包含原客户的密钥、授权状态、聊天记录、数据库、附件和客户演示材料。它不是已经完成生产验收的成品。

## 1. 产品定位与交付范围

目标交付形态是 **企微机器人 + 手机周报 H5 + 企微文档**，不要求客户使用独立 PC 管理后台。

当前代码仍保留早期 PC 管理页面，且工作计划、日报、周报、反馈和发送队列仍依赖 SQLite。人员、企业名录和新企业已具备企微普通表格连接能力。**“全部业务数据以企微文档为准、彻底去掉 PC 管理依赖”属于下一阶段工作，不是本仓库已经完成的能力。**

## 2. 已实现的产品功能

| 业务需求 | 产品功能与实现方式 | 边界 |
| --- | --- | --- |
| 员工快速开始使用 | 私聊引导、绑定码、身份确认、使用帮助 | 绑定码不是公开共享的通用密码；必须先初始化人员 |
| 周一制定工作计划 | 收集事项、计划目标、计量单位与背景，形成计划记录 | 目标变更需要明确处理，不能由模型自行改写 |
| 日常工作随手记录 | 接收企微文字及附件消息，保存原始记录，模型整理日报草稿 | 不代表所有附件类型都能完整识别；扫描件/OCR不在默认保证范围 |
| 防止 AI 误记账 | 员工查看文字草稿，回复确认或修改后再形成正式记录 | 模型输出不是已确认事实 |
| 进度可计算 | 按事项保存计划及完成事实，区分累计/增量，计算完成率 | 口径不清时保留待补充，不把未知当零 |
| 与企业名录匹配 | 从企微表格同步企业和人员，关联工作记录 | 两张极简表模式目前仅支持一位老板、一位员工；另有多人员标准表模式 |
| 发现新企业 | 名录未命中时检索候选，员工确认/补充后写入“新企业”普通表格 | 检索失败须如实提示；新企业确认独立于日报确认 |
| 查看新企业信息 | 周报企业名称可打开详情；展示企业情况、需求及跟进等信息 | 联系人和联系方式不放到公开周报；进入正式名录后不再作为新企业展示 |
| 员工查看周报 | 按周查看工作摘要、事项进度、原因与管理者反馈 | 当前移动端入口见下文 |
| 管理者看整体进展 | 团队汇总、事项/员工视角、员工明细、周间比较、反馈 | 最新客户静态稿的全部交互并不等于动态服务已经同步实现 |
| 反馈闭环 | 页面提交反馈，保存原文，生成通知任务，由机器人发送 | 不允许 AI 擅自改写领导意见；纯归集不等于新增判断 |
| 主动提醒 | 周计划提醒、工作日日报提醒、周报生成及消息发送队列 | 需要网关持续在线，发送成功还需真实账号验收 |
| 可追溯留存 | 原始记录、确认状态、修订记录、审计、结构化归档和数据库备份 | 目前留存主要在本地数据库，并非完整企微文档存储 |
| 控制模型成本与风险 | 规则计算、结构化输出校验、有限重试、提示词约束、上下文筛选与调用记录 | 未配置模型时默认 Mock；不代表真实智能整理效果 |

### 最新业务分类

已确认的业务方向为：重点企业完成进度、培训与活动、企业服务与对接、综合事务、其他工作。客户静态演示采用首项通栏、其余四项两列布局。

**这套五分类及最近的静态交互尚需统一落入运行时数据模型和移动端页面。** 原客户静态 HTML 含业务数据，未收入公开仓库；不要把动态页面现状误认为最终视觉验收版。

## 3. 主要业务流程

### 3.1 身份绑定

1. 实施人员准备人员名单、角色和上下级关系，导入/同步。
2. 为员工生成绑定码并私下分发。
3. 员工私聊机器人发送 `绑定 绑定码`，核对身份后回复 `确认绑定`。
4. 系统把企微身份与业务人员关联；后续消息使用该身份归属。

一个管理者也可以记录自己的工作。角色决定可查看/反馈的范围，不应把“负责人”和“有自己任务”当成互斥身份。

### 3.2 计划、日报与进度

1. 员工提交本周计划，例如“本周走访5家企业，完成2场活动”。
2. 每天描述完成事实、企业需求、受阻原因与下一步。
3. 系统保留原文，识别事项、企业及数量；模型负责语言整理，不负责凭空补齐事实。
4. 机器人返回简短文字草稿。员工回复 `确认日报`，或 `修改日报：更正内容`。
5. 确认后记录进入周报计算。同一天修改面向用户呈现最新内容，底层保留追溯信息。

进度按同口径的完成数÷计划数计算。百分比变化应使用百分点（PP），例如60%到80%为+20 PP，不是+20%。计划外工作应独立标识，不偷偷计入原计划完成率；咨询不能仅因涉及企业就算作一次走访。相关最终展示仍需按上线清单统一验收。

### 3.3 新企业收集

1. 员工说“今天拜访某企业”，名录中找不到匹配项。
2. 系统尝试检索企业资料，展示候选和不确定信息，不默认同名即同企业。
3. 员工通过 `补充新企业` 补充信息，并回复 `确认新企业` 后写入企微表格；也可取消。
4. 表中保留行业、主营业务、人员规模、注册资本、法人、注册地址，以及意向区域、用房需求、预计落地时间、阶段和下一步等。
5. 周报读取新企业资料，展示业务摘要；正式企业名录命中后停止新企业详情入口。

当前检索适配包含 Bing RSS 和针对特定供应商的实验性检索实现，不是任意模型天然支持联网。换模型必须单独验证检索接口、授权、费用与可用性；无结果和网络失败不能混淆。待确认新企业会话状态还需补持久化，避免进程重启丢失。

### 3.4 周报与反馈

1. 汇集已确认计划、每日完成事实、原因和已有反馈。
2. 生成员工周报，管理者查看团队事项与员工概况。
3. 管理者查看具体事项/员工后提交反馈。
4. 保存反馈原文并创建通知任务，网关向员工发送提醒。
5. 员工查看周报中的反馈，后续工作记录继续形成闭环。

客户最新静态稿要求：姓名打开员工周报并可返回，事项文案打开事项详情；已完成/未完成/计划外筛选只影响明细、不改变总览卡片。此部分需和动态端统一后再做生产验收。

## 4. 代码结构

```text
apps/
  gateway/       企微 WebSocket、绑定、对话、流式回复、主动发送
  api/           业务编排、HTTP接口、目录同步、新企业、周报与反馈
  web/           移动周报H5，以及尚未剥离的旧PC管理页面
  agent-service/ 可选独立模型服务
  shared/        项目级配置加载
packages/
  agent/         Agent接口、Mock/方舟/OpenAI兼容适配、提示词与校验
  domain/        业务类型、默认规则、日期与统计口径
  persistence/   SQLite建表、仓储、审计与状态持久化
scripts/         名录同步、数据库备份
config/          无敏感信息的配置样例
infra/           Linux容器镜像
compose.yaml     API与机器人网关的部署编排
```

日常请求的路径是：企微用户 → WebSocket 网关 → 业务规则/模型 → 草稿 → 人工确认 → 保存 → 周报 H5。网页反馈走 API → 发送队列 → 网关 → 企微员工。企微文档连接由隔离授权的 CLI 完成。

## 5. 数据存放与配置

| 内容 | 当前存放位置 |
| --- | --- |
| 人员/企业名录 | 企微普通表格，导入本地业务副本 |
| 新企业资料 | 企微普通表格；链接在 `.runtime/new-companies.json` |
| 计划/日报/周报/反馈/绑定/队列/审计 | `.runtime/data/poc.sqlite` |
| 附件/备份/企微文档授权 | `.runtime/` 下隔离目录 |
| 模型/机器人/端口等运行配置 | `.runtime/wecom.env` 等本项目配置文件 |

配置读取次序为 `wecom.env` → `local-poc.env` → `deepseek.env` → `local-run.env`，后者覆盖前者；均位于 `.runtime/`。不会自动借用宿主机其他机器人的配置。新部署建议只使用 `wecom.env`，避免隐藏覆盖。

### 名录表格式

- 极简两表模式：人员表包含 `人员、绑定码、角色`，企业表包含 `企业名称`。当前仅一位老板和一位员工，不能直接用于几十人团队。
- 标准模式：同一普通表格中的“员工”“企业”两个子表。员工列为 `员工编号、姓名、部门、角色、上级员工编号、状态`；企业列为 `企业编号、企业名称、行业、园区、负责员工编号、联系人、联系电话、企业概况、状态`。角色支持员工、组长、部门负责人，状态和上下级关系会校验。此模式可用于继续验证多人员接入。
- 新企业表完整表头以 `apps/api/src/new-companies.ts` 的 `NEW_COMPANY_COLUMNS` 为准，不能随意改列名。
- 同步失败或内容截断时停止处理，不能据此清空已有数据。自动双向同步、删除冲突及外部编辑合并仍需完善。

## 6. 本地开发与验证

环境：Node.js 24、pnpm 11.9.0。项目使用 Node 内置 SQLite，不能用旧版本 Node 替代。

```bash
pnpm install --frozen-lockfile
pnpm check
mkdir -p .runtime
cp .env.example .runtime/wecom.env
```

Windows 可使用 `New-Item -ItemType Directory -Force .runtime` 和 `Copy-Item .env.example .runtime/wecom.env`。

编辑配置，至少填写随机的 `POC_ACCESS_CODE`；这是遗留管理接口所需的保护值，不能因客户只看 H5 就留空。随后：

```bash
pnpm api
# 另一个终端；配置真实机器人后才启动，避免与已有实例抢连
pnpm gateway
```

API 默认 `http://127.0.0.1:3000`；健康接口 `/api/v1/health`。移动入口 `/weekly.html`，员工公开演示入口 `/employee-weekly.html` 需配置对应已存在的人员。空库不会自动生成真实员工，也不会自动为新客户创建企微表格或授权。

`AGENT_PROVIDER=mock` 只适合离线测试；真实服务选择 `openai_compatible` 或 `ark`，填入供应商的地址、模型和密钥。模型名称及是否提供搜索能力以实际账号为准，仓库不附带任何可用密钥。

## 7. 新服务器部署

详细步骤见 [部署手册](docs/DEPLOYMENT.md)。本次只整理部署资产，**未连接或修改任何新旧生产服务器**。

部署采用一个 API 容器、一个企微网关容器，共享同机 `.runtime` 数据目录。只在主机回环地址暴露 API 的3000端口；由服务器的 HTTPS 反向代理接入域名。机器人通过出站 WebSocket 连接企微，不需要公开网关健康端口。

同一个 Bot ID 只保留一个活动网关，切换服务器前先停旧实例。初期按单机单实例部署；SQLite与当前发送队列不应直接扩容为多副本。

## 8. 正式上线前必须补齐

1. 明确企微文档作为业务主数据的表结构、唯一ID、幂等写入、分页、并发、失败重试、对账与恢复规则，并迁移日报/周报/反馈。
2. 去除客户使用路径中的 PC 管理依赖，补实施端命令/配置入口；不能只隐藏菜单。
3. 将五类事项、计划外工作、完成/未完成筛选、员工详情返回与最新反馈交互同步到动态页面。
4. 完成多人名录和汇报关系联调，不能使用两人极简模式替代实际团队。
5. 新企业确认状态持久化，搜索适配可配置；验证目标模型的JSON异常、超时与额度耗尽处理。
6. 选择周报链接的可见范围和反馈身份保护。公开只读链接不等于允许任何访客代管理者写反馈；当前公共演示模式不应承载真实客户敏感数据。
7. 补齐企微周报留存的正式发布/更新/回写链路。历史原型的客户表格和一次性留存脚本未收入此仓库，不能宣称这里已有全自动智能表格归档。
8. 新服务器验证 HTTPS、域名访问、备份恢复、重启保活、真实企微消息收发及手机反馈闭环。源码测试通过不等于以上验收通过。

## 9. 安全与发布原则

- 不提交 `.runtime`、`.env`、私钥、令牌、授权状态、数据库和客户文件。
- 已在聊天或其他非密钥系统分享过的密钥，正式上线前应更换；不要复用演示凭据。
- 不在日志输出模型密钥、机器人 Secret 或完整文档授权信息。
- 不公开上传原项目 Git 历史。本仓库从脱敏后的工作文件建立新历史。
- 默认不开放PC管理端到互联网；服务器反向代理应限制管理员入口，并在放行客户H5前完成权限验收。
- 本仓库公开便于查看与协作，尚未选择开源许可证；公开可见不等同于授予任意再分发许可。
